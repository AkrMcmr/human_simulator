# 人間モデルのロジックを育てる外側のループ

個体内の学習は、固定された計算規則の中で記憶や予測を更新します。この仕組みは、その計算規則自体を開発者・LLMが変更し、旧版との比較から次の変更を選ぶためのものです。

`仮説登録 → 候補実装 → ソース固定 → 旧版/候補/寄与無効の評価 → 採否 → 次の仮説`

候補は係数に限りません。記憶の持ち方、注意、予測、動機、行動選択、学習則のコード変更を扱います。実行中にLLMへ判断を依頼せず、開発時にLLMが調査・実装・結果の考察を担当できます。

## 実行できる操作

ルートで`npm run evolve -- ...`を実行します。

| 操作 | 結果 |
| --- | --- |
| `register --spec FILE` | 仮説、反証条件、追加仮定、親サイクル、モデルID、主要改善基準を保存。評価器・環境を固定 |
| `seal --id ID` | 実装済みの旧版・候補・寄与無効版とソースを固定 |
| `run --id ID` | 同じ評価器で3版を測り、必須能力、悪化、寄与無効の一致、指定した改善幅を判定 |
| `replay --id ID` | 保存済みの測定値と判定を再計算し、一致を確認。保存結果を上書きしない |
| `decide --id ID --outcome retain-candidate/revise/reject --reason TEXT` | 候補保持・再設計・棄却と理由を追記。ゲート未達の候補保持を拒否 |
| `status` / `next` | 各サイクルの状態と、悪化箇所・未達仮説・次の研究課題を表示 |

結果は`cycles/<ID>/`に保存します。registration、seal、result、next、decisionを分け、既存ファイルは上書きしません。コードや評価条件が固定後に変われば実行を拒否します。修正時は新しいIDと`parentCycle`を使い、失敗も系譜に残します。測定結果は版管理するコンパクトな能力評価で、全ステップの履歴ではありません。

## 新しいロジックを作る手順

1. [現在地](../../docs/STATUS.md)、[中期目標](../../docs/MIDTERM_GOALS.md)、`npm run evolve -- next`から一つの問題を選ぶ。
2. `specs/predictive-retrospective.json`を別名へコピーし、仮説、機構、反証条件、追加仮定、次の問いを書く。新規研究なら`registration: prospective`、結果を既に見た移行・再評価なら`retrospective`。`parentCycle`には前のサイクルを指定する。
3. 必要な課題を[研究ループ](../LOOP.md)に従って設計する。下記の現行評価器の範囲を確認し、評価の計算・閾値・条件を先に固定して`register`、Gitへコミットする。
4. 人間モデルの新しい実装と独立した版を追加し、`models.ts`に旧版・候補・寄与無効版の入口を登録する。旧版を残し、同じIDの挙動を黙って変えない。
5. 変更に応じたテストを実行し、コードをコミット。`seal`して固定記録もコミットする。`dirty: true`を隠さず、再現に必要な変更をすべて保存する。
6. `run`で測定。未達でも数値が有効なら結果と次課題を保存し、終了コード1を返す。NaNや形式不正など、測定自体が壊れた場合はエラーとして修正サイクルへ進む。
7. 結果・副作用・仮定の増加を検討し`decide`。`STATUS`と研究判断を更新し、GitHubへ反映する。次のLLM/開発者には`next`の課題と親IDを渡す。

寄与無効版には、新しく追加した仕組みだけを取り除いた実装を渡します。旧版との一致を要求する設計です。構造上完全一致できない変更では、その理由と適切な対照を新しい評価仕様で定義し直してください。

## 今回動く範囲と、今後拡張する部分

評価器はspecの`study`で選びます。省略か`core-v1`は**基礎能力10項目**、`world-v1`は**通常worldの8条件比較**（[protocol](../protocols/world-v1.json)、[研究コード](../studies/world-v1.ts)）です。`primary`にその評価器のチェックIDと正の`minimumGain`を指定すると、開発・確認の両群で改善幅も判定します。空配列なら副作用確認だけで、`improvementGate`は必ずfalseです。world-v1のサイクルでもcore-v1の回帰と寄与無効の一致を常に確認します。core-v1のシードは既知なので、名前がvalidationでも新しい未使用確認には数えません。world-v1のシードも`predictive-normal-world-m1`で観察済みです。

評価器ハッシュには評価コード、契約、world、experiments、simulationの実行器と乱数、両protocol、engine、CLI、依存ロックを含めます。モデルハッシュにはhumanのソースと二つの登録簿（`packages/simulation/src/models.ts`、`research/evolution/models.ts`）を含めます。

最初のサイクル`predictive-retrospective`は既存予測政策の**事後的な移行・動作確認**です。過去のpolicy-v1研究を事前登録し直したものではありません。主要改善基準を空にして、基礎能力を維持することだけを確認します。二つ目の`predictive-normal-world-m1`はworld-v1を主要基準にした子サイクルで、`study:world` CLIで結果を確認した後に登録したためretrospectiveです。この結果をもとに候補は既定human 0.2.0になりました（既定化はこのCLIの外で、[判断0004](../decisions/0004-normal-world-m1.md)に記録）。以後の新しい仮説は`human-0.2.0`を旧版としてprospectiveで登録し、結果を見る前にコミットしてください。

新しい能力の実験を自動発明したり、論文を自動収集したり、コードを無人で書き換えるエージェント/定期ジョブはこのCLIに含めません。開発者や任意のLLMが外側の作業者です。状態形式は現行`ModelAdapter`に依存しており、別形式の記憶へ移る際はアダプターの更新が必要です。

注意、記憶への介入、合図などまだ測れない改善は、まず個別protocolと評価器を追加し、旧版も同じ課題で評価します。次に`study`の選択肢としてengineへ接続し、機構固有の改善と既存coreの回帰を別々に記録します。`nextStudy`はその未接続の課題を失わないための必須欄です。評価器を変えたら既存登録を書き換えず、新しいサイクルを登録します。評価器ハッシュが変わると旧サイクルの`replay`は拒否されますが、保存済みの結果と判断はそのまま証拠として残ります。

## 採用と証拠

`retain-candidate`は「実験候補として残す」です。既定のsimulation/UIの変更は別の実装・版更新として、対象課題の証拠と互換性を確認して行います。このコマンドで既定版を変更することはありません。ユーザーが認めた開発範囲内では、LLMも理由を記録して候補の採否を進められます。

ハッシュと追記型ファイルは事故や比較条件の混在を検出するためのものです。改ざん耐性のある署名やアクセス制御ではありません。登録の前後関係と旧実装の保存にはGitの履歴を併用します。初期のローカル/GitHubのコミットIDの差は[版管理](../../docs/development/VERSIONING.md)を参照。

高精度化は得点の単調増加を意味しません。反証による棄却、必要な仮定の削減、別条件での弱点の発見も次の改訂に使います。人間への妥当性は実測データとの別の検証が必要です。
